# Repository Guidelines

## Назначение и границы проекта

«Герда» — локальный голосовой помощник на Python 3.11 для Herdr и Codex. Английский процесс обрабатывает F6/F7, а отдельный русский worker — F8.
Английский процесс отслеживает завершённые ответы Codex и озвучивает их. Отдельный контейнерный сценарий выполняет пакетную
расшифровку аудио и видео.

Сохраняйте эти два контура раздельными:

- `assistant/` — диктовка, озвучка ответов и интеграция с Herdr;
- `app/` — пакетная транскрибация через Docker;
- `tests/` — автоматические тесты;
- `scripts/` и `systemd/` — установка, управление и пользовательские unit-файлы;
- `models/`, `input/` и `output/` — локальные модели и рабочие данные, не
  являющиеся исходным кодом.

Не переносите бизнес-логику между `assistant/` и `app/` ради формального DRY.
Общие части выделяйте только тогда, когда они действительно не зависят от
конкретного пользовательского сценария.

## Команды разработки и проверки

- `uv run --python 3.11 --no-project python -m unittest discover -s tests -v` — полный набор unit-тестов.
- `.venv-english/bin/python -m assistant.daemon --check` — проверка загрузки локальных
  моделей без запуска микрофона.
- `docker compose config` — проверка итоговой Docker Compose-конфигурации.
- `docker compose run --rm gigaam` — реальная пакетная транскрибация файлов из
  `input/`; требует Docker и загруженных моделей.

Минимальный детерминированный gate для изменения кода — полный набор unit-тестов.
При изменении загрузки моделей или Docker-контура дополнительно запускайте
соответствующие проверки выше. Не объявляйте аппаратную или системную интеграцию
проверенной, если фактический микрофон, аудиовыход, Herdr, systemd или Docker не
использовались.

## Стиль Python

Используйте четыре пробела, аннотации типов для публичных границ и
`from __future__ import annotations` в новых модулях. Имена модулей, функций и
локальных переменных пишите в `snake_case`, классов — в `PascalCase`, констант —
в `UPPER_SNAKE_CASE`. Предпочитайте `pathlib.Path`, небольшие функции и явные
зависимости. Не добавляйте новый formatter, linter или framework без отдельной
необходимости.

## Архитектура операций

Каждое новое или существенно изменяемое пользовательское действие оформляйте
как одну самостоятельную операцию в самом узком подходящем контексте. Здесь
`<context>` — `assistant` или `app`:

```text
<context>/operations/<operation>/
├── entity/
├── interface/
│   ├── usecase.py
│   ├── repository.py       # только для состояния или хранения
│   └── gateway.py          # только для внешних систем
├── usecase/
├── repository/
│   └── <backend>/          # filesystem, sqlite и т. п.
├── gateway/
│   └── <capability>/       # herdr, audio, subprocess и т. п.
└── presentation/
    ├── voice/
    ├── tray/
    ├── cli/
    └── http/               # только если HTTP действительно появится
```

Создавайте только действительно нужные каталоги. Например, голосовая команда без
состояния может состоять из `entity`, `interface/usecase.py`, `usecase` и
`presentation/voice`; искусственный repository ей не нужен. Название операции
должно описывать одно действие, например `submit_prompt`, `speak_last_result` или
`toggle_auto_speak`.

Для каждой операции соблюдайте следующие правила:

- Публичный интерфейс use case содержит один метод `execute`, принимает локальный
  для операции `Input` и возвращает локальный `Result`; интерфейсы зависимостей
  описывайте узкими `Protocol`. Ожидаемые отказы выражайте понятными типами ошибок,
  а не строковыми флагами.
- Use case не импортирует use case, entity или repository другой операции. Он
  принимает решения только для своей операции и не становится диспетчером
  нескольких действий.
- Presentation владеет одной ручкой и входным форматом конкретного канала:
  распознанной голосовой фразой, callback tray, аргументами CLI или HTTP DTO. Она
  нормализует и проверяет вход, после успешной проверки вызывает `execute` ровно
  один раз и отображает результат без бизнес-решений.
- Stateful-операция владеет своим repository-интерфейсом, реализацией, форматом
  хранения и преобразованием данных. Не создавайте общий repository с методами
  нескольких операций и не передавайте persistence в stateless-операцию.
- Внешние зависимости оформляйте как consumer-owned gateway операции. Herdr,
  Docker, subprocess, микрофон, аудиовыход и часы не должны незаметно вызываться
  из entity или бизнес-логики. Долговременное хранение в файлах относится к
  repository; прочая работа с файловой системой — к узкому gateway.
- Entity одной операции не является глобальной доменной моделью. Небольшое
  осознанное дублирование между операциями предпочтительнее связанности use case.
- `assistant/daemon.py`, `assistant/tray.py` и точки входа только читают
  process-level конфигурацию, собирают зависимости, регистрируют presentations и
  управляют жизненным циклом. Новые бизнес-решения в composition root не добавляйте.

Не создавайте глобальные `domain`, `common`, `shared`, `utils`, универсальные
`Service`/`Manager` или union-dispatcher слои. Независимые от продукта технические
примитивы допускаются в узко названном `assistant/technical/<capability>/`; этот
код не должен содержать голосовые команды, настройки продукта, presentation DTO
или правила конкретной операции.

## Совместимые фасады и точки входа

`assistant/core.py`, `assistant/preferences.py` и `assistant/tray_core.py` — только
совместимые фасады для прежних импортов. `assistant/daemon.py` и
`app/transcribe.py` — composition roots. Не возвращайте в них бизнес-логику,
работу с хранилищем или прямую реализацию внешних протоколов: новое поведение
должно целиком принадлежать соответствующей operation-local структуре.

При удалении совместимого импорта сначала перенесите его потребителей и тесты.
Не смешивайте удаление фасада с несвязанной функциональной задачей.

## Тестирование

Новую структуру тестов зеркальте по операциям:

```text
tests/operations/<operation>/
├── test_usecase.py
├── test_presentation_<channel>.py
└── test_repository_<backend>.py
```

Существующие тесты верхнего уровня остаются допустимыми до миграции соответствующей
функциональности. Называйте тесты по наблюдаемому поведению. Покрывайте успешный
сценарий, отказ и граничные условия. В unit-тестах подменяйте gateway и repository
простыми fake/stub-реализациями; не требуйте реального микрофона, Herdr, systemd,
Docker или сети.

Для изменений платформенной интеграции заранее разделяйте два контура проверки:

- детерминированный — unit-тесты, fixtures, проверка конфигурации и контрактов;
- реальный локальный — микрофон/аудиовыход, Herdr, systemd, Docker и модели на
  целевой машине.

Результаты этих контуров сообщайте отдельно. Mock или fixture подтверждает контракт
адаптера, но не считается реальной проверкой оборудования или внешнего процесса.

## Конфигурация и безопасность

Process-level настройки читаются из переменных окружения в точке сборки и
передаются зависимостям явно. Не читайте окружение из entity или use case.
Не коммитьте `.venv`, скачанные модели, содержимое `input/` и `output/`, локальные
state-файлы, записи голоса, секреты и пользовательские абсолютные пути. Изменения
systemd и установочных скриптов проверяйте вместе: их пути и команды запуска должны
оставаться согласованными.

## Коммиты

Делайте небольшие тематические коммиты с кратким повелительным заголовком. Не
включайте в коммит пользовательские или несвязанные изменения. В описании PR или
передаче результата перечисляйте выполненные тесты и отдельно отмечайте, какие
проверки реального локального контура не запускались.
